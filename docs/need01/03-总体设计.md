# 03 — 总体设计

## 3.1 设计目标回顾

- 调用方（`Session`、`app.rs`、`cli`）**不感知协议细节**，只认 `AssistantReply` / `StreamEvent` / `ToolDef` / `ChatMessage`。
- chat 链路**零行为变化**：只做"移动 + 加 trait"，不改逻辑。
- Responses 客户端与 `OpenAiClient` 并列，共享一切可共享（SSE 切分、鉴权、超时、代理、截断、单测基建）。

## 3.2 `LlmClient` trait（新增 `crates/core/src/llm/client.rs`）

```rust
use async_trait::async_trait; // 或手写 BoxFuture；见 §3.2.1
use crate::config::Resolved;
use crate::llm::openai::{AssistantReply, StreamEvent};
use crate::llm::types::{ChatMessage, ToolDef};

#[async_trait] // 若不想引入依赖，改手写 `fn chat<'a>(…) -> Pin<Box<dyn Future…>>`
pub trait LlmClient: Send + Sync {
    fn model(&self) -> &str;
    fn reconfigure(&mut self, cfg: &Resolved);
    async fn chat(&self, messages: &[ChatMessage], tools: Option<&[ToolDef]>)
        -> anyhow::Result<AssistantReply>;
    async fn chat_stream<F>(&self, messages: &[ChatMessage], tools: Option<&[ToolDef]>, on_event: F)
        -> anyhow::Result<AssistantReply>
    where F: FnMut(StreamEvent) + Send;
    async fn validate(&self) -> anyhow::Result<()>;
    async fn list_models(&self) -> anyhow::Result<Vec<String>>;
}

/// 工厂：调用方唯一入口
pub fn build_llm_client(cfg: &Resolved) -> anyhow::Result<Box<dyn LlmClient>> {
    match cfg.protocol {
        ProtocolKind::Chat => Ok(Box::new(OpenAiClient::new(cfg)?)),
        ProtocolKind::Response => Ok(Box::new(ResponsesClient::new(cfg)?)),
    }
}
```

§3.2.1 async trait 说明：workspace 当前无 `async-trait` 依赖。若不愿加依赖，两种省事方案：
  (a) trait 方法返回 `Pin<Box<dyn Future<Output=…> + Send + '_>>`（手写 4 个方法，约 20 行样板）；
  (b) `Session` 改泛型 `Session<C: LlmClient>`（零依赖、零虚函数，但 `app.rs`/`cli` 所有 `Session` 类型位都要加泛型参数，改动面大）。
推荐 (a) 或加 `async-trait`（workspace 统一加一行，最省事）。`chat_stream` 的 `F: FnMut` 泛型 + async 组合在 trait 里较别扭，可把回调改为 `&mut dyn FnMut(StreamEvent)`（session.rs 现有调用点 `|evt| {...}` 照常传入，无改动）。

`ProtocolKind` 放 `config.rs` 还是 `llm`？放 `config.rs`（`ProviderDef`/`Resolved` 就在那里，避免循环依赖；`llm` 引用 `config` 已是现状）。

## 3.4 可共享 helper（`client.rs` 或 `llm/shared.rs`）

从 `openai.rs` 抽出（逻辑**逐行照搬**，只换位置）：

| helper | 来源 | 说明 |
|---|---|---|
| `new_http_client() -> reqwest::Client` | `OpenAiClient::new` L212–224 | 超时 600s + connect 10s + `proxy_from_env` |
| `auth(req, api_key)` | `auth` L284–289 | bearer 鉴权 |
| `truncate(s, max)` | L514–516 | 错误文案截断（`crate::util::truncate_chars` 包一层） |
| `http_error(status, text)` | `chat` L324–326 内联格式串 | `"模型端点返回 {status}: {截断}"`，两客户端共用，保证文案一致 |
| `SseParser` | `sse.rs` | 原样复用 |
| 流泵骨架 | `chat_stream` L359–374 | 抽成 `async fn pump_sse(resp, on_data: impl FnMut(String) -> ControlFlow) `？可选。最小方案：不抽，responses.rs 里照抄 15 行循环（`break 'stream` 改为"收到 completed 即停"）。推荐先照抄（省一次抽象），待稳定后再抽。 |

不共享的（各写各的，强行统一反而坏事）：`build_body` vs `build_response_body`、`extract_usage`（字段名不同）、`ToolCallAccumulator` vs `FunctionCallAccumulator`（索引语义不同：`index` vs `output_index + item_id`）、`apply_stream_line` vs `apply_response_event`。

## 3.5 `responses.rs` 结构（新建，约 550 行含单测）

```rust
pub struct ResponsesClient { http, base_url, api_key, model }   // 与 OpenAiClient 同构

// —— 请求构造 ——
fn chat_to_response_input(messages: &[ChatMessage]) -> (Option<String>, Vec<Value>)
//   -> (instructions, input)，映射表见 04 §4.1
fn tool_defs_to_response_tools(tools: &[ToolDef]) -> Vec<Value> // 见 04 §4.2
fn build_response_body(&self, messages, tools, stream) -> Map<String, Value>

// —— 非流式 ——
fn parse_response_response(text: &str) -> Result<AssistantReply>
fn response_output_to_reply(output: &[Value], usage: Usage) -> Result<AssistantReply>
fn extract_response_usage(v: &Value) -> Usage  // input_tokens/output_tokens

// —— 流式 ——
struct FunctionCallAccumulator { calls: Vec<AccToolCall> }  // 照抄 ToolCallAccumulator
impl FunctionCallAccumulator {
    fn ensure(&mut self, output_index: usize);
    fn set_item(&mut self, output_index, id, call_id, name); // output_item.added
    fn push_delta(&mut self, output_index, delta: &str);     // arguments.delta
    fn finish_item(&mut self, output_index, item: &Value);   // output_item.done 补齐
    fn finish(self) -> Vec<ToolCall>;                        // 只收有 name 的
}
fn apply_response_event(line, content, reasoning, usage, acc, on_event) -> Result<bool> // done=true 仅当 completed

impl ResponsesClient {
    pub fn new(cfg: &Resolved) -> Result<Self>;
    pub fn model(&self) -> &str;
    pub fn reconfigure(&mut self, cfg: &Resolved);
    fn url(&self) -> String;            // {base}/responses
    fn models_url(&self) -> String;     // {base}/models（与 chat 同）
    pub async fn list_models(&self);
    pub async fn validate(&self);       // 最小 Responses 请求：input=[{role:user,content:"hi"}]
    pub async fn chat(&self, messages, tools);
    pub async fn chat_stream<F>(&self, messages, tools, on_event: F);
}
impl LlmClient for ResponsesClient { … } // 薄转发
impl LlmClient for OpenAiClient { … }    // openai.rs 内加，薄转发
```

`validate` 细节：chat 版是 `self.chat(&[user("hi")], None)`；Responses 版是 `self.chat(&[user("hi")], None)` 走 Responses 转换（天然得到 `input:[{role:user,content:"hi"}]`），"有内容/无内容但成功都算可用"的语义不变。

## 3.6 数据流（两种协议统一视角）

```
Session.messages: Vec<ChatMessage>            // 内存唯一真相（两种协议相同）
      │ chat: 透传                              │ response: chat_to_response_input()
      ▼                                         ▼
POST /chat/completions                      POST /responses
{model,messages,tools,stream}               {model,instructions,input,tools,stream}
      │ choices[0].message                    │ output[]
      │ choices[].delta + [DONE]              │ response.*.delta + completed
      ▼                                         ▼
AssistantReply{content,reasoning_content,tool_calls,usage}   // 同一中间表示
      │
      ▼ Session 主循环（不动）→ execute_tool_call → record(ChatMessage::tool) → 下一轮
```

## 3.7 不做什么（防蔓延）

- 不给 `ChatMessage` 加 Responses 专用变体（D4）。
- 不在首版支持 `previous_response_id`（服务端会话状态与本地 jsonl 历史是两套账，对账复杂；全量 `input` 每次重发，行为正确、只是费 token——与 chat 现状一致）。
- 不统一两套解析函数（字段名/事件名差异大，硬统一会制造"看似共用实则处处分支"的代码）。
