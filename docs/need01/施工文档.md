# need01：给模型 Skill 写 / 改 / 删能力（双级别 + 全局强授权）施工文档

> 状态：待施工（设计稿）
> 对应需求：新增内置工具，让模型拥有 skill 的 write / edit / delete 能力；同时支持 global 与 project 双级别；操作 global 必须用户明确授权。
> 基线代码：`crates/core/src/skills.rs`（~691 行）、`crates/core/src/tools/mod.rs`、`crates/core/src/tools/file.rs`、`crates/core/src/session.rs`（`PermKind` / `check_permission` / `build_skill_tool_def` / `run_skill`）、`crates/core/src/permissions.rs`、`crates/core/src/undo.rs`、`crates/tui/src/app.rs`（`/skills` / 斜杠分发 / 补全）、`crates/core/src/config.rs`（`data_dir()`）
> 前置阅读：`docs/skill分析.md`、`docs/使用说明.md` 第 7 节

---

## 0. 目标与非目标

### 0.1 目标（必须做到）

1. 新增 3 个模型可调用的内置工具：`skill_write`（新建 / 覆盖）、`skill_edit`（改 SKILL.md）、`skill_delete`（删整个技能目录）。
2. 双级别：`scope=project`（`<cwd>/.znaide/skills/<name>/`）与 `scope=global`（`~/.znaide/skills/<name>/`，即代码里的 User 层，`ZNAIDE_DATA_DIR` 可改根）。
3. 全局强授权：任何落到 global skills 的写 / 改 / 删（含绕路：`write_file` / `edit` / `run_shell_command` 直接碰 global 路径）都必须弹一次明确确认；`BypassPermissions` 也不能跳过；无头模式直接拒绝并给可操作提示；仅 `Yolo` 透传放行（需打日志，见 4.5）。
4. 复用现有校验与安全：`valid_name`、`frontmatter name 一致性`、`entry 相对路径 containment`、undo 快照。
5. 热加载不受影响：写完下个回合 / `/skills` 即时可见（现 `scan` 无缓存，不用改）。

### 0.2 非目标（V1 不做）

- 不做 skill 版本管理 / 市场 / 从 URL 安装。
- 不做 `builtin-skills/` 的直接写；一律拒绝并引导复制到 global / project。
- 不做删除目录的“一键完整回滚”（undo 只能按文件回滚，见 6.3 的降级方案）。
- 不改 `skill` 调用工具（读 / 触发）的现有语义。

## 2. 方案决策（先定死，避免施工扯皮）

### D1：3 个独立工具，不做统一 `skill_manage`

- 工具名：`skill_write` / `skill_edit` / `skill_delete`。
- 理由：与 `write_file` / `edit` 心智对齐；卡片可直接显示 `skill_write「foo」`；schema 简单，弱模型误调率低；权限映射清晰。3 个 def 约 +600 tokens，可接受。
- 拒绝方案：单个 `skill_manage{op,...}` —— `oneOf` / 条件必填对弱模型不友好，权限分支藏在工具内部，UI 卡片还要二次解析 op。

### D2：`scope` 枚举用 `project | global`

- Schema：`"scope": {"type":"string","enum":["project","global"],"description":"project=当前项目 .znaide/skills（默认），global=全局 ~/.znaide/skills（需明确确认）"}`。
- 内部 `global → SkillSource::User`（`data_dir().join("skills")`），`project → cwd.join(".znaide/skills")`。
- 兼容：解析时把 `"user"` 视为 `"global"` 别名（历史文档叫“用户级”，模型可能吐 user）。
- 缺省：`scope` 缺省按 `"project"` 处理（防误写全局），但 Schema 仍建议必填以逼模型显式思考。

### D3：权限种类新增 `PermKind::SkillGlobal`，project 复用 `PermKind::Write`

- `PermKind` 新增变体：
  ```rust
  pub enum PermKind {
      Write,
      Command,
      SkillGlobal, // 全局 skill 写/改/删：Bypass 也不放行，必须单次明确确认
  }
  ```
- `session.check_permission` 加分支（伪代码）：
  ```rust
  PermKind::SkillGlobal => {
      if self.mode == Mode::Yolo { Allow }
      else if self.events.is_none() { Deny("全局 skill 修改需交互确认，无头模式已拒绝…") }
      else { 发 PermissionRequest{kind: SkillGlobal, title:"全局技能修改确认", body, warning:None} 单次确认，不吃 file_always/command_always }
  }
  ```
- 为什么不用 `warning=Some` 复用 Command 的 hazard 通道？`warning` 会让 TUI 红字渲染 + 禁“总是允许”，语义接近但标题还是“命令执行确认”，误导。新增变体让标题/正文精确，且以后可单独审计。

### D4：拦截放在 `session` 分发层，不放在 `tools/file.rs` 内

- `tools::execute` 拿到的 `ToolContext.permission` 在 `after_permission` 里已经被替换为 `BypassPermissions/Yolo`（`session.rs:1270-1275`），工具内看不到原始档位，做不了“ Bypass 仍要问 global”的判断。
- 所以 scope 感知 + 路径护栏必须在 `session::execute_tool`（`need_perm` 附近，约 `session.rs:1210-1244`）做，那里有 `self.mode` / `self.events` / `self.cwd` 全上下文。
- `tools/skill.rs` 只做纯文件操作 + 校验，不做权限判断（与现有 `file.rs` 分工一致：权限由 session 把关）。

### D5：`builtin-skills/` 只读

- 任何 `scope` 解析都不指向 builtin；路径护栏把落到 `builtin_dir()` 的写 / 删一律 `Deny` 并提示“复制到 global/project 再改”。

### 3.1 SKILL.md 生成格式（与迁移格式对齐）

```
---
description: <desc>
disable-model-invocation: true/false（false 可省略不写，保持干净；建议只在 true 时写）
entry: <entry>（有才写）
```

- `name` 不写入 frontmatter（目录名即真相，避免不一致告警；与 `migrate_commands_from` 口径一致）。
- `description` 为空允许，但给出 warning 文案（模型判断依赖它）。
- 正文为空拒绝（`body.trim().is_empty() → Err`）。

## 4. session.rs 改造（权限 + 分发，核心）

### 4.1 `PermKind` 加变体 + `check_permission` 分支

位置：`session.rs:20-25` 定义，`715-814` 实现。

```rust
// 定义
pub enum PermKind { Write, Command, SkillGlobal }

// check_permission() 新增分支（放在 Yolo 透传之后、events.is_none 分支之前）：
if kind == PermKind::SkillGlobal {
    if self.mode == Mode::Yolo {
        return PermissionResult::Allowed; // 超级模式语义：一切放行，但建议 emit Notice 留痕
    }
    if self.events.is_none() {
        return PermissionResult::Denied(
            "全局技能修改需用户明确确认，无头模式已拒绝。如确需执行请用 project 级，或在交互模式确认后重试".into()
        );
    }
    // 交互：单次确认，不吃 file_always / command_always
    let (tx, rx) = oneshot::channel();
    self.emit(SessionEvent::PermissionRequest {
        kind, // TUI 按 kind 渲染标题，见 7.1
        title: "全局技能修改确认".to_string(),
        body, // 调用方传入：如 "skill_write global/foo\n目标: /home/u/.znaide/skills/foo/SKILL.md"
        warning: None,
        tx,
    });
    // select rx / cancel，与现有 Write 分支同模板；always=true 也只当单次（不置 file_always）
    ...
}
```

注意：现有 `check_permission(kind, cmd)` 的 `cmd` 参数对 Write 类是空串；SkillGlobal 需要把“将要做什么”塞进 `body`，建议加一个新方法 `check_skill_global(&mut self, summary: String)` 包一层，避免复用 `cmd` 语义混乱。

### 4.2 工具分发：3 新工具的 scope 感知

位置：`session.rs:1210-1244` 的 `need_perm` 附近。当前结构：

```rust
let need_perm = match name.as_str() {
    "write_file" | "edit" => Some(PermKind::Write),
    "run_shell_command" => { ...特殊处理... }
    _ => None,
};
```

改为：

```rust
// 1) 新工具：先解析 scope，再定 kind
"skill_write" | "skill_edit" | "skill_delete" => {
    let scope = parse_scope_from_args(&args); // "global"/"user"→Global，其余→Project
    let summary = format!("{} {} / {}", name, scope.label(), skill_name_from_args(&args));
    match scope {
        Project => { let perm = self.check_permission(PermKind::Write, "").await; return self.after_permission(name, args, perm).await; }
        Global  => { let perm = self.check_skill_global(summary).await; return self.after_permission(name, args, perm).await; }
    }
}
// 2) 护栏：write_file / edit 落到 global/builtin → 提级
"write_file" | "edit" => {
    let target = extract_path_arg(&args); // "path"
    match classify_skill_path(&resolve(&self.cwd, &target), &self.cwd) {
        Builtin => return deny("内置技能只读…复制到 global/project 再改"),
        Global  => { let perm = self.check_skill_global(format!("{name} {target}")).await; return self.after_permission(...).await; }
        _ => { 正常 Write 流程 }
    }
}
// 3) run_shell_command：只做启发式护栏（见 4.6），其余走原 Command 流程
```

`skill`（调用）工具本身不动，仍走 `run_skill` 老路（正文注入无权限面，entry 按 Command 权限）。

### 4.3 `after_permission` 不动

- 复用现有 `after_permission(name, args, perm)`（`session.rs:1248`）：Denied 发卡片 + `操作未执行: reason`；Allowed 以 `Bypass/Yolo` 跑 `tools::execute`。新工具同样走它，卡片自动有 `ToolStarted/Finished`。

### 4.4 工具卡片命名

- 沿用 `skill` 的做法：`skill_write「foo」` / `skill_edit「foo」` / `skill_delete「foo」`，scope 追加 `(global)` 后缀以便用户一眼识别风险，如 `skill_write「foo(global)」`。实现位置与 `session.rs:1142-1147` 的 card 逻辑并列，建议抽一个小函数 `skill_mgmt_card(name, args)`。

### 4.5 Yolo 与无头口径（必须写进帮助文案）

| 模式 | project skill 写改删 | global skill 写改删 | write_file 直写 global 路径 |
|------|---------------------|---------------------|---------------------------|
| Ask（询问） | 弹确认 | 弹“全局技能修改确认” | 提级为全局确认 |
| AcceptEdits（编辑放行） | 自动放行 | 仍弹全局确认 | 仍弹全局确认 |
| BypassPermissions（全自动） | 自动放行 | 仍弹全局确认 | 仍弹全局确认 |
| Yolo（超级） | 放行 | 放行（建议 emit Notice“全局技能已在 Yolo 下修改”留痕） | 放行 |
| 无头（events=None） | Ask 拒，其余放行（同现有 Write） | 一律拒绝 | 一律拒绝 |

### 4.6 路径护栏细节（防绕过，必做）

- `write_file` / `edit`：`path` 参数绝对化后 `classify_skill_path`：
  - `Builtin` → Deny（无论何种模式，Yolo 除外）：“内置技能只读（…/builtin-skills/…），请用 skill_write scope=global/project 另存一份再改”。
  - `Global` → 走 `SkillGlobal` 单次确认。
  - `Project` → 正常 `Write` 流程（不提级，避免打扰正常项目开发）。
- `run_shell_command`：命令串是自由文本，无法精确判定。最小实现：
  - 若命令串词法含 `data_dir/skills` 或 `builtin-skills` 字样 **且** 含 `rm|rmdir|shred|unlink|mv|mkdir|tee|>|>>|sed -i|chmod|chown` 等写删语义 → 视为 `Uncertain`，走一次 `SkillGlobal` 确认（或至少 Command 确认 + 正文提示）。V1 允许保守：直接按 `SkillGlobal` 问一次，误伤可接受（模型很少用 shell 直接动 skills 目录，有 `skill_*` 工具后更少）。
  - 不追求完美解析，文档中明确写“shell 直改 skills 目录会被多问一次，请优先用 skill_* 工具”。
- `glob/grep/list/read`：只读，不拦截。

### 5.2 执行流程（含 undo）

- `skill_write(ctx, args)`：
  1. 反序列化参数；`parse_scope`；`valid_name` 不过 → `ToolError`（把规则原文返回，模型可自改）。
  2. 调 `skills::write_skill_file` 写盘。
  3. 若 `overwrite` 且文件已存在 → 先 `undo::backup_for_session(ctx.session_id, &skill_md, "skill_write")` 再写（`write_skill_file` 内部做或工具层做，二选一，建议工具层做以统一 action 命名）。
  4. 返回 `"已写入 <scope>/<name>（<字节数>）。/skills 可查看，下回合可调用。"` 并附 warnings（如 description 为空）。
- `skill_edit`：先 `backup_for_session(..., "skill_edit")` 再 `edit_skill_file`。
- `skill_delete`：先 `delete_skill_dir` 拿到文件清单 → 逐个 `backup_for_session(..., "skill_delete")` → 已在函数内 `remove_dir_all` 或工具层删（建议函数内删，清单仅用于备份——注意顺序：先备份再删，所以函数应拆 `list_skill_files` + `remove` 两步，或把备份回调传进去；最简：工具层先 list+backup，再调删除。见 6.3）。
- 所有 `ToolError` 文案给模型看，要可操作（如“已存在，请加 overwrite:true 或改用 skill_edit”）。

### 5.3 entry 脚本内容怎么写？

- V1：`skill_*` 只管 `SKILL.md`；`scripts/*` 仍用 `write_file` / `edit` 写。
  - project scripts：正常 Write 权限。
  - global scripts：落到 global 路径护栏，自动提级为全局确认（4.6），与 SKILL.md 口径一致。
- 模型工作流文案（写进 `skill_write` 描述或系统提示）：`先 skill_write 建 SKILL.md（含 entry 声明）→ 再 write_file 写 scripts/xxx → 必要时 skill_edit 修正 entry`。
- V2 可选：给 `skill_write` 加 `files:[{path,content}]` 原子创建附件；V1 不做以控制 scope。

## 6. 校验、安全与 undo

### 6.1 复用清单（不另起炉灶）

- 名合法性：`skills::valid_name`。
- `name == 目录名`：写路径即目录名，天然一致；`edit` 不允许改名（改名 = 写新 + 删旧，模型分两步）。
- `entry` containment：绝对路径 / `..` 拒绝（与 `load_skill` 同规则，建议抽 `validate_entry(entry) -> Result<(), String>` 供读写共用）。
- 正文非空；`{args}` 不强制（有些技能无需参数）。

### 6.2 路径穿越防御

- `skill_dir_for` 后断言 `starts_with(scope_dir)`（防 `name` 含 `/`/`..`，虽然 `valid_name` 已拦 `..` 与 `/`，纵深防御）。
- session 护栏的 `classify_skill_path` 必须绝对化 + 词法归一后再 `starts_with` 比较；Windows 注意大小写与 `/` `\`（用 `Path` 比较而非字符串 contains）。

### 6.3 undo 语义

| 操作 | 快照 | 回滚 |
|------|------|------|
| `skill_write` 新建 | 无（文件原不存在，`backup` 返回 None） | 删文件即回滚（V1 提示手动删；V2 可记“新建” tombstone） |
| `skill_write` 覆盖 / `skill_edit` | `SKILL.md` 快照，action=`skill_write` / `skill_edit` | `/undo` 按文件回滚（现有能力直接可用） |
| `skill_delete` | 目录下每个文件逐个快照，action=`skill_delete` | 按文件逐个回滚（需手动重建目录；V1 在返回文案里说明 + 给出原路径；V2 做 trash 整目录恢复） |
| global scripts 经 `write_file` | 同现有 `write_file` 快照 | 同现有 |

- `/undo` 列表会自动出现 `skill_write/skill_edit/skill_delete` 的 action 名（`is_external` 逻辑不动）。
- TUI 的 `file_writes` 计数（`app.rs:1756`）把 3 新工具名加进去，否则删除类操作不计入状态栏统计。

## 11. 风险与回滚

| 风险 | 对策 |
|------|------|
| 模型误写 global（scope 填错） | scope 缺省 project；Schema 强调 global 会弹窗；全局单次确认兜底 |
| `write_file` 绕过 | session 护栏必做（S4），单测覆盖 |
| shell 绕过（`rm -rf ~/.znaide/skills`） | 启发式多问一次 + 文档引导用 `skill_*`；不承诺完全拦截（与现有 shell 判定同为启发式，见 `permissions.rs` 头注） |
| 删除后无法一键恢复 | 返回文案明示 + undo 按文件备份；V2 做 trash |
| Windows 路径比较大小写 | 用 `Path::starts_with` + 必要时 `to_lowercase` 归一，单测覆 Windows 风格路径 |
| 上下文膨胀 | 3 def 精简描述；`skill` 调用工具不动 |

回滚：本需求纯新增 + session 分发加分支，无存量格式变更；回滚 = revert S3/S4 提交，`skills/` 下已建文件不受影响（`scan` 照常读）。
