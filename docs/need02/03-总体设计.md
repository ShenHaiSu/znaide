# 03 总体设计

## 1. 分层（一句话）

- **开关**是配置（跟 provider 走，存文件）；**值**是运行时身份（跟 Session 走，不存文件）。
- `Resolved` 只带 `session_header_enabled: bool`；具体头值由 `Session` 在创建/恢复后 `push` 进 client。

## 2. 模块划分

```text
Config（开关持久）
 ├─ ProviderDef.session_header: bool        // 按家存
 └─ Resolved.session_header_enabled: bool   // 随身携带
         │
         ▼
SetupWizard（初始化采集）
 ├─ Step::SessionHeader（Provider 之后）
 └─ draft() → Resolved{ session_header_enabled }
         │
         ▼
Session（值供给）
 ├─ Session::new() 生成 session_id 后 → client.set_session_header(id/enabled)
 ├─ load_history() 切换 id 后 → 同步刷新 client
 └─ reconfigure() → 开关变化则更新，连接池不重建
         │
         ▼
LlmClient（头注入）
 ├─ OpenAiClient{ session_header: Option<String> }
 └─ ResponsesClient{ session_header: Option<String> }
     └─ auth()/发射点 .header("x-opencode-session", v)
```

## 3. 时序（首启）

```text
用户选 Provider(A)
  → 向导切 Step::SessionHeader：“是否为 A 启用会话头？(Y/n)”
  → 用户回车（默认 Y 或 N，见 05 §2 二选一，推荐默认 Y）
  → 后续 ModelSelect → ProtocolSelect → ApiKey → … → Verifying（validate 带探针头）
  → 保存 config.json（该家 session_header=true/false）
  → 建 Session（真实 session_id）→ client.set_session_header(真实 id)
  → 之后所有 chat/responses 请求自动带头
```

`/config` 重开、`--resume`、CLI 覆盖时序见 05 §4 / 06 §3。

## 4. 为什么不用 `extra_headers: HashMap`

- 首版只有一个头、一个布尔语义，HashMap 会把向导、校验、文档复杂度翻倍。
- `ProviderDef` 加一个 `bool` 即满足"选完供应商就问要不要开"；`Resolved` 加一个 `bool` 即打通全链路。
- 04 §5 预留升级路径：将来真要通用头时，把 `bool` 迁移为 `HashMap` 的一次迁移即可，`auth()` 的注入点不动。

## 5. 并发与生命周期

- 头值存 `Option<String>`，`clone` 成本可忽略；`chat/chat_stream` 均为 `&self`，读值无锁。
- `set_session_header` 取 `&mut self`，只在建会话/恢复/重配三处调用，不在热路径加锁。
- 流式请求的头在 `http.post(url)` 构造瞬间确定，流中途换会话不影响当前流。
